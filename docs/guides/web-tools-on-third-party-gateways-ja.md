# サードパーティゲートウェイで WebSearch / WebFetch が動かない理由と対処

> 本書は、Claude Code をサードパーティゲートウェイ（tern のようなローカルゲートウェイ経由を含む）に向けた際に `WebSearch` と `WebFetch` が失敗する理由と、その対処を説明します。文中のアドレス・ポート・モデル名はサンプルです。実際の値に読み替えてください。
>
> tern は `serve` 起動時と `check` の両方で、サードパーティゲートウェイに該当するプロバイダーを自動的に列挙します。本書はその警告の根拠です。

## まず結論

`WebSearch` と `WebFetch` は `ANTHROPIC_BASE_URL` のメッセージ経路を**使いません**。これらはクライアント側の独立した機能であり、一部は Anthropic 側のサービスの協力を必要とします。そのため tern が `/v1/messages` を完璧に転送しても、この 2 つのツールは完全に動かない場合があります。これはゲートウェイのバグではなく、ゲートウェイ側で修正できるものでもありません。

2 つのツールは失敗理由も異なり、エラーメッセージで見分けられます：

| ツール | 典型的なエラー | 性質 | 原因の所在 |
|---|---|---|---|
| `WebSearch` | `API Error: 400 The input you provided is invalid` | 検索リクエストが拒否された、またはエンドポイント未実装 | ゲートウェイに検索エンドポイントがない |
| `WebFetch` | `Unable to verify if domain <ドメイン> is safe to fetch` | **ドメイン安全性の事前チェックに失敗**。ページ取得自体が始まっていない | チェックサービスがゲートウェイ経由で届かない |

`WebFetch` のメッセージは特に誤解されやすい点です。これは実際の取得**以前**に、Claude Code 内蔵のドメイン安全性チェックとして発生します。そのチェックがサービスに届かない場合、対象サイト自体に到達できるかどうかに関わらず、同じメッセージが出ます。

## 誤解しやすい現場

同じエラーが出ていても、マシンのネットワーク自体は**通っている**ことがよくあります。例えば：

```powershell
curl -s -o /dev/null -w "%{http_code}" --max-time 8 https://example.com
```

`200` が返っても矛盾ではありません。curl はシステムプロキシまたは直接経路を使いますが、この 2 つのツールは独自の出口を使います。したがって「ブラウザで開ける」ことは「ツールが動く」ことを意味しません。

## tern 側でやること

**検出と通知だけ**です。リクエストを書き換えたり、これらのツールの代理送信をしたりはしません（実現不可能です）。

- `tern check` は末尾に「联网工具 / ネット系ツール」セクションを出し、該当プロバイダーを列挙します
- `tern serve` は起動時に、サードパーティプロバイダーごとに警告を 1 件出します

判定基準は、上流のホストが `api.anthropic.com` かどうかです（ホストのみを比較し、ポート・パス・userinfo は無視）。これから導かれる 2 つの境界ケース：

- **誤検出**：Anthropic 互換プロトコルを話し、かつ実際に検索もサポートしている上流も、第三者として判定されます。「tern が壊れた」と誤解されるくらいなら、一文多く出る方がましです。
- **偽装は回避**：`https://api.anthropic.com@evil.com/` のように本当のホストを userinfo に隠すアドレスは、`@` 以降だけを見るため正しく第三者と判定されます。

## 対処方法

### 方法 1：settings.json で無効化する（ネット不要なら最も確実）

日常的にウェブ参照を使わないなら、権限レイヤーで無効化し、Claude Code が呼び出さないようにします：

```json
{
  "permissions": {
    "deny": ["WebSearch", "WebFetch"]
  }
}
```

注意点：

- これは**ユーザーグローバル設定**（`~/.claude/settings.json`）で、すべてのプロジェクトに適用されます。
- 既存の設定と**マージ**してください。ファイル全体を上書きしてはいけません。`env` や `includeCoAuthoredBy` などの既存キーは保持してください。
- deny ルールはセッション起動時に読み込まれます。新しいセッションを開くのが確実です。現在のセッションで即座にブロックされた場合は、設定がホットリロードされたことを意味します。
- 影響するのは 2 つのウェブツールのみです。会話やコーディング能力には影響しません。
- tern はこのファイルを管理しません。CC Switch など他のツールが管理している場合、永続化はそのツールの書き込みに従います。

### 方法 2：WebFetch の事前チェックをスキップする（WebFetch だけ復活させたい場合）

ゲートウェイに実際の出口があり、ドメイン安全性チェックだけで阻まれているなら、そのチェックをスキップできます：

```json
{
  "skipWebFetchPreflight": true
}
```

これは `WebFetch` にしか効果ありません。`WebSearch` は上流が検索エンドポイントを認識していない問題なので、スキップしても無駄です。

tern には「プリセット」の概念がないため、このキーは自分で `~/.claude/settings.json` に書く必要があります。これを必要とするプロバイダーは、通常「ページは取得できるが検索はできない」という挙動になります。

### 方法 3：公式エンドポイントに戻す

両ツールは Anthropic 公式エンドポイントでは完全にサポートされています。復活させるには、`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN` などを公式デフォルトに戻してください。あるいはモデル名先頭の `プロバイダー/` を外し、公式エンドポイントに直接処理させるのでも構いません。本書で追加した設定も可逆です。`permissions.deny` と `skipWebFetchPreflight` のキーを削除するか、必要に応じて片方だけ残してください。

## トラブルシューティング

| 症状 | 診断 |
|---|---|
| `400 The input you provided is invalid` + `WebSearch` | ゲートウェイに検索機能がない。検索を無効化するか、対応エンドポイントを使う |
| `Unable to verify if domain ... is safe to fetch` + `WebFetch` | ドメインチェックサービスの出口がない。`skipWebFetchPreflight: true` を試す |
| 両方同時にエラー | ゲートウェイがどちらにも非対応。方法 1 を推奨 |
| ブラウザは動くがツールは失敗 | 想定内。出口経路が異なるだけで反例ではない |
| deny 追加後もエラーが出る | 設定が未適用。`~/.claude/settings.json` に書けているか確認し、セッションを再起動する |
| `tern check` で自分の第三者が列挙されない | アドレスが `api.anthropic.com` またはその偽装。上の判定基準を参照 |

## 補足

- `WebSearch` の可否はアカウント側の権限にも依存します。公式エンドポイントでも結果が返る保証はありません。
- 本書の警告文と、`tern check` / `tern serve` が出力する文章は同一の出所です。片方を直せばもう片方も追随します。
