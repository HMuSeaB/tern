# tern の使用量を上流の請求書と突き合わせる

> 本文が扱うのは：`tern usage` の出力を上流プロバイダの請求書とどう照合するか、どの差が両者の集計範囲や課金規則の違いから来るのか（想定の内で説明できる）、そしてどれが tern 側の実際の誤りを意味するのか（修正に値する）。日付・モデル名・金額はすべて脱感してある。
>
> 最初にやるべきは `tern usage --from <日付> --to <日付>` である。上流の請求書は会計期間で区切られる。それに対して `--days` は毎日ずれるローリングウィンドウなので、固定日付の請求書にそれを突き合わせると、必ず数日のずれが出る。

## まず結論

**tern の数字と上流の請求書は、項目ごとに一致しない。一致を目ざすべきでもない。** 差には二種類ある。

- **集計範囲・規則の差**：両者が数えている請求の集合が違う。または、同じ集合に違う課金規則を当てている。これは規則的で、説明でき、定量できる。本文で列挙するのはこれである。
- **実際の誤り**：tern がトークン数を転記し間違えた。価格の選択を誤った。倍率を落とした。これにはパターンがなく、差の原因を説明できない。

したがって照合の目的は「一致させる」ことではない。**差の全部を、以下のいずれかの節に帰属させる**ことである。そこで説明できなかった残りが、調べる価値のある部分だ。

## 出力のしかた

```powershell
tern usage --from 2026-10-01 --to 2026-10-31 --by model
tern usage --from 2026-10-01 --to 2026-10-31 --by day --recent 0
```

- `--by model` は、実際に課金されたモデル別の内訳を出す。請求書のモデル明細に最も近い表である。
- `--by day` は、日別の内訳を出す。差がどの日に集中しているかを特定する。
- `--recent 0` は、末尾の請求一覧を消す。総額を比べる段階では、それはノイズでしかない。

出力はテキストのみである。JSON / CSV はない。等幅フォントで桁が合っているので、ブロックごとコピーすればよい。

**出力する前に、価格テーブルが安定していることを確認する。** `tern price set` は過去の記録を遡って再計算する（README に「歴史記録は自動的に再価格設定される」とある動作である）。つまり価格を埋めた後で同じ区間を出力すると、以前とは違う答えになる。先に `tern price list` を一度見て、照合の途中で価格を変えないこと。

## 固有差の一覧

数字をどれだけ動かせるかで並べてある。最初の二つで、差の大部分が説明できることが多い。

| # | 差 | 請求書に対する tern | 大きさ |
|---|---|---|---|
| 1 | 中断・ストリーム途中での失敗 | tern が高い | 大きくなりうる |
| 2 | 未定価モデル | tern が低い | 大きくなりうる |
| 3 | キャッシュ読み書きフィールドの口径 | 不定 | 中 |
| 4 | モデル交換後、エコーされたモデル名で課金 | 不定 | 大きくなりうる |
| 5 | `costMultiplier` | 不定 | 固定比率 |
| 6 | 区間の端がローカル日で切られる | 不定 | 端の数日に集中 |
| 7 | tern を通った流量だけを数える | tern が低い | 使い方による |

### 1. 中断と、ストリーム途中での失敗

tern が記録するのは、**自分が見たトークン**である。場合が三つある。

| 場合 | tern が記録するもの | 上流が通常すること |
|---|---|---|
| 2xx を得る前に失敗（4xx / 5xx / レート制限 / 接続失敗） | トークン 0・コスト 0。失敗を 1 件だけ数える | 通常も何も計上しない。**この場合に差は生じない** |
| ストリームの途中でエラー | エラーまでに解析できた usage ブロックで課金する | 請求を丸ごと計上しないこともある |
| クライアントが途中で切断（面板では「中断」） | 生成されたトークンをそのまま課金する | 多くは生成分を課金する。ただし中断ストリームを課金しない中継所もある |

だから実際に差を開けるのは、後の二つである。切り分けに使えるものはこうだ。

```powershell
tern usage --from 2026-10-01 --to 2026-10-31 --recent 0
```

失败の件数は、出力の「失败（N 次，不计入上面的模型 token）」その行に書かれている。最初の場合（2xx 以前の失败）は、トークンもコストも 0 である。もう総額には影響しない。

困ったことに、残りの二つはそうはいかない。**中断のトークンとコストは、実際に総額に計上される。** それなのに、コマンドライン出力には「中断」の行がない。`--by role` は角色ごとの請求数とトークンを出せるが、中断は角色に混ざって独立行にならない。一件ずつ見るには、面板の「最近请求」表しかない。各行が 成功 / 中断 / 失败 と标记されている。

実践的な見立てはこうである。差が長いセッション、サブエージェント、Ctrl+C で中断したタスクに集中しているなら、ほぼこの類だ。中継所では、これらが課金されないことがよくある。

### 2. 未定価モデル

未定価のモデルは、`tern usage` が自分から列出する。

```
⚠ 3 个请求的模型没有定价，花费未计入：
```

トークンは記録されている。しかし金額は記録されていない。つまり**この欄が空でない限り、tern の費用総額は必ず低く出る。** 不足分は、これらのモデルのトークンを正しい価格で計算した金額に相当する。

価格を埋める方法：

```powershell
tern price set <モデル名> <入力> <出力> [<キャッシュ読取> [<キャッシュ書込>]]
tern price sync          # または models.dev から同期
```

歴史記録は自動的に再計算される。もう一度出力すれば一致する。**七つのうち、直すとゼロになるのはこれだけだ。** だから照合では最初に確認する。

### 3. キャッシュ読み書きフィールドの口径

Claude 系のキャッシュには、金が二段ある。書込（`cache_creation_input_tokens`。定価よりわずかに高い）と、命中（`cache_read_input_tokens`。定価より大幅に安い）。tern は、上流がエコーしたこの二つのフィールドを、それぞれに課金する。

差は、上流がエコーを変えることから生じる。

- キャッシュフィールドを**まったくエコーしない**上流がある。0 を入れる。tern はその入力を定価で課金する。結果は高くなる。
- 命中を `input_tokens` にまとめて、内訳を出さない上流もある。tern はそれを定価入力として扱う。同じく高くなる。
- 公式とは粒度の違うエコー（ブロックごとでなく、請求ごとの合計）をする上流もある。

見分け方はこうだ。面板首屏の「缓存命中率」を見る。Claude Code が明らかにコンテキストを再利用している（長いセッション、同じファイルを繰り返し読む）のに、命中率が 0 近いなら、上流がエコーしていない可能性が高い。実際に命中していないわけではない。

### 4. モデル交換後、エコーされたモデル名で課金する

tern は価格の突き合わせを、**上流がエコーしたモデル名**で行う。どうしても合わない場合だけ、自分が送った名前にフォールバックする。理由はこうだ。中継所が請求モデルをもう一度マッピングすることが多く、実際に課金されるのはエコーされた側だからである。

これは照合上の落とし穴になる。**上流がエコーする名前と、請求書の課金モデル名が同じ文字列でないと、価格の突き合わせは失敗する。** 典型的な場合：

- 上流が `claude-sonnet-4-6` をエコーし、請求書には `claude-sonnet-4-6-20260218` のように日付付きで書かれている。一致せず、未定価に落ちる。
- 上流が自分のエイリアス（`step-5-preview`）をエコーし、請求書は公式名を使う。同じ問題。

だから第 2 類（未定価）は、第 4 類の**症状**であることが多い。未定価のリストに項目があるときは、まずその文字列を請求書と見比べること。

面板首屏の「模型被换」告警は、まさにこれを捕まえるためのものである。客户端が要求したモデルと、実際に課金されたモデルが違う。その告警が空でない日は、この節を読む価値がある。

### 5. `costMultiplier`

中継所が割引課金をする場合、プロバイダに `"costMultiplier": "0.3"` を設定し、tern は倍率を適用する。差はここから生じる。

- 請求書が**定価**で、割引は別の周期で返還される。
- 請求書が別の倍率を使う。段階割引で、あなたの区間が別の段に落ちている。
- 倍率の設定が誤っている。または途中で変えた。変える前に記録した請求は、古い倍率のままである。

これは**固定比率**なので、最も見分けやすい。tern の数を請求書の数で割ればよい。定数になったら、これである。

### 6. 区間の端がローカル日で切られる

tern の `day` 列は、**マシンのローカルタイムゾーン**の自然日で切られる。`--from` / `--to` もローカル日である。上流の請求書は UTC で切られるかもしれない。独自の期間（例えば毎月 1 日 00:00 UTC 決済）で切られるかもしれない。

結果はこうだ。期間の最初と最後の 1～2 日の請求が、別の区間に落ちる。量は大きくない。しかし総額が**いつも少しだけずれ**、しかも他の差を全部説明し終えた後も、ずれたままになる。

見分け方はこうだ。`--by day` で最初と最後の日を見る。残った差がそのうちの一日の量に近ければ、これである。

### 7. tern を通った流量だけを数える

`usage.db` にあるのは、tern を通った請求だけである。上流に直接行ったセッションは入っていない（`ANTHROPIC_BASE_URL` を設定していない別のターミナル、または cc-switch の別のスロット）。

これは**接入した直後の数日**に最も目立つ。接入より前の使用量は、そもそも tern になかったからである。面板の「接入」ページが「未接入」と表示していた期間は、そのまま欠落だ。

## 照合チェックリスト

順に進む。各段階で、一類型ずつ除外できる。

1. `⚠ 3 个请求的模型没有定价，花费未计入：` のような行が出ていないか。出ている → 価格を埋め、再出力する。第 2 類型がゼロになる。
2. 未定価リストのモデル名は、請求書の課金名と同じ文字列か。違う → 第 4 類型。価格キーは、請求書の名前に合わせる必要がある。
3. 面板に「模型被换」告警が出ているか。出ている → その日は、課金モデルと交換後のモデルの両方を請求書と照合する。
4. tern ÷ 請求書 が定数に近いか。そう → 第 5 類型。`costMultiplier` を確認する。
5. 残った差が、期間の端の一日ぶんに近いか。そう → 第 6 類型。タイムゾーン境界。
6. 残った差が、長いセッション・サブエージェント・Ctrl+C で中断したタスクに集中しているか。そう → 第 1 類型。中断課金。一件ずつの確認は、面板の「最近请求」表でしかできない。
7. キャッシュ命中率が、体感より明らかに低いか。そう → 第 3 類型。上流がキャッシュフィールドをエコーしていない。
8. どれも違う。→ ここで初めて、tern が間違えたと疑う価値がある。期間、`--by model` の出力、請求書の明細を一緒に記録し、`tern check` の出力を添える。

## 備考

- 第 1・3・4 類型は、方向が不定である（高くも低くもなる）。したがって「tern が請求書より高い」ということ自体は、何も言わない。まず帰属させること。
- 第 2 類型は、直すとゼロになる唯一のものである。だから常に最初だ。
- 面板首屏の三つの告警（模型被换 / 失败 / 未定价）は、本文の第 4・1・2 類型に対応する。首屏が汚れていない日は、照合がずっと速く進む。
- 本文の判準は、`tern usage` の出力と源を同じくする。`day` 列はローカル日で切られ、課金モデルは上流がエコーしたものを優先し、倍率はプロバイダ設定から取られる。一か所を直すれば、両方に届く。
