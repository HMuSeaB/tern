# 用 tern 的用量和上游发票逐项对账

> 本文说明：怎么把 `tern usage` 导出的数字和上游供应商开出的发票摆到一起，哪些差异是**两边口径不同**（正常，要解释），哪些是 **tern 真的算错了**（要修）。示例中的日期、模型名、金额均已去敏。
>
> 对账的第一步是 `tern usage --from <日期> --to <日期>`——上游发票按账期开，而 `--days` 是个每天都在漂的滚动窗口，拿它对一张固定日期的票，永远差几天。

## 结论先说

**tern 的数字和上游发票不会逐项相等，也不该追求相等。** 差异分两类：

- **口径差异**：两边数的不是同一批请求，或对同一批请求的计费规则理解不同。这类差异有规律、可解释、可定量。本文列的就是这一类。
- **真错**：tern 把 token 数抄歪了、价格匹配错了、倍率没生效。这类没有规律，对不上也说不清为什么。

所以对账的正确目标不是"两边相同"，而是**差异能被本文的某一节解释掉**。解释不掉的剩下那一块，才是要查的问题。

## 导出来

```powershell
tern usage --from 2026-10-01 --to 2026-10-31 --by model
tern usage --from 2026-10-01 --to 2026-10-31 --by day --recent 0
```

- `--by model` 给"按实际计费的模型"的拆分，这是和发票的模型明细最接近的一张表。
- `--by day` 给按天拆分，用来定位差异集中在哪几天。
- `--recent 0` 关掉末尾的请求明细——对总额时那一段只是噪音。

目前只有文本输出，没有 JSON / CSV。要贴进表格就整段复制，列是等宽对齐的。

**导出前先确认价格表是稳定的**：`tern price set` 会回头重算历史记录（README 里说的"历史记录自动补价"）。所以补过一次价格之后，同一个区间的导出结果会和补之前不一样。对账前先 `tern price list` 看一眼，中途别再改。

## 固有差异清单

按"能把数字推多远"排序。前两类通常就解释了绝大部分差距。

| # | 差异 | tern 相对发票 | 量级 |
|---|---|---|---|
| 1 | 中断 / 流式中途出错的请求 | 偏高 | 可很大 |
| 2 | 未定价模型 | 偏低 | 可很大 |
| 3 | 缓存读写字段的口径 | 不定 | 中 |
| 4 | 模型被换后按回显模型名计价 | 不定 | 可很大 |
| 5 | `costMultiplier` | 不定 | 固定比例 |
| 6 | 账期边界按本地日切 | 不定 | 集中在边界那几天 |
| 7 | 只统计经过 tern 的流量 | 偏低 | 取决于你怎么用 |

### 1. 中断 / 流式中途出错的请求

tern 记下的是**它看见的 token**，分三种情况：

| 情况 | tern 记多少 | 上游通常怎么办 |
|---|---|---|
| 拿到 2xx 之前就失败（4xx / 5xx / 限流 / 连接失败） | 0 token、0 成本，只记一次失败 | 通常也不计。**这一类不产生差异** |
| 流式响应中途出错 | 按出错前已经解析到的 usage 块计费 | 可能整笔不计 |
| 客户端中途断开（面板里标「中断」） | 照计已经产生的 token 和成本 | 多数按实际生成计；有些中转站对中断的流不计 |

所以真正会拉开差距的是后两种。隔离它们的办法有限，先说清楚有什么：

```powershell
tern usage --from 2026-10-01 --to 2026-10-31 --recent 0
```

输出的「失败（N 次，不计入上面的模型 token）」那段给的是失败**次数**——拿到 2xx 之前就失败的那一类，token 和成本都是 0，已经不影响总额。

麻烦的是另外两种：**中断的 token 和成本是实打实记进总额的**，而命令行输出里没有"中断"这一档。`--by role` 能给每个角色的请求数和 token，但中断混在角色里不单独成行。要逐条看，只有面板「最近请求」那张表——每条都标了状态（成功 / 中断 / 失败）。

实践上的判断：差异集中在长会话、子代理、被 Ctrl+C 打断的任务上时，基本就是这一类。这类任务在中转站那边经常是不计费的。

### 2. 未定价模型

`tern usage` 会显式列出它们：

```
⚠ 3 个请求的模型没有定价，花费未计入：
```

这些请求的 token 记了，钱没记。所以**只要这一节非空，tern 的总花费就一定偏低**，偏低多少就是这几个模型的 token 按正确价格算出来的数。

补法：

```powershell
tern price set <模型名> <输入价> <输出价> [<缓存读价> [<缓存写价>]]
tern price sync          # 或从 models.dev 同步
```

补完历史记录自动重算，再导一次就能对上。**这是全部七类差异里唯一一类"补完就归零"的**，所以对账第一步先看它。

### 3. 缓存读写字段的口径

Claude 系的缓存分两段钱：写入（`cache_creation_input_tokens`，比全价贵）和命中（`cache_read_input_tokens`，比全价便宜）。tern 按上游回显的这两个字段分别计价。

差异来自上游回显得不一样：

- 有的上游**根本不回显**缓存字段，一律填 0。tern 就会把这部分输入按全价计 —— 结果偏高。
- 有的上游把命中也并进 `input_tokens`，不单列。tern 会把它当全价输入 —— 同样偏高。
- 有的上游回显的粒度和官方不是一回事（比如按请求汇总而不是按 block）。

判断办法：看面板首屏的「缓存命中率」。如果 Claude Code 明显在复用上下文（长会话、反复读同一批文件），而命中率接近 0，那大概率是上游没回显，不是真的没命中。

### 4. 模型被换之后按回显的模型名计价

tern 优先按**上游回显的模型名**匹配价格，其次才是发给它的名字。理由是中转站常把请求模型再映射一次，实际计费的是回显的那个。

但这带来一个对账上的坑：**如果上游回显的名字和发票上的计费模型名不是同一个字符串**，价格就匹配错了。典型情况：

- 上游回显 `claude-sonnet-4-6`，发票上写 `claude-sonnet-4-6-20260218` 这种带日期的 —— 匹配不上，落到未定价。
- 上游回显的是它自己的别名（`step-5-preview`），发票用官方名 —— 同样匹配不上。

所以第 2 类（未定价）经常是第 4 类的**症状**而不是原因。看到未定价列表里有模型名时，先拿它和发票上的名字对一眼字符串。

面板首屏的「模型被换」告警就是抓这件事的：客户端要的模型 ≠ 实际计费的模型。那条告警非空的日子，这一节就值得看。

### 5. `costMultiplier`

中转站按折扣计费时，供应商上配 `"costMultiplier": "0.3"`，tern 按倍率算。差异来自：

- 发票开的是**原价**（折扣在另一个账单周期里返）。
- 发票用的是另一个倍率（比如阶梯折扣，你这个区间落在另一档）。
- 倍率配错了，或者中途改过 —— 改之前记的请求还是老倍率。

这一类是**固定比例**的，最好认：把 tern 的数除以发票的数，如果是个常数，基本就是它。

### 6. 账期边界按本地日切

tern 的 `day` 列按**本机时区**的自然日算，`--from` / `--to` 也是本地日。上游发票可能按 UTC、可能按他们自己的账期（比如每月 1 日 00:00 UTC 结算）。

后果：账期头尾那两天的请求会被分到不同的区间里。量级不大，但会让总额**永远差一点点**，而且补上别的差异之后还是差。

判断办法：`--by day` 看头尾两天的量。如果差异 ≈ 其中一天的量，就是这一类。

### 7. 只统计经过 tern 的流量

`usage.db` 里只有流过 tern 的请求。直连上游的会话（另一个终端里没设 `ANTHROPIC_BASE_URL`、或者用了 cc-switch 的另一个槽位）不在库里。

这一类在**刚接进来**的那几天最明显：接线之前的历史用量本来就不在 tern 这儿。面板「接入」页显示「未接入」的时段，就是缺口。

## 对账检查表

按顺序走，每步都能排掉一类：

1. `⚠ N 个请求的模型没有定价` 是空的吗？不是 → 补价格，重导，归零第 2 类。
2. 未定价列表里的模型名，和发票上的计费模型名是同一串吗？不是 → 第 4 类，价格键要对着发票的名字填。
3. 首屏有「模型被换」告警吗？有 → 那几天的计价模型和被换后的模型都要和发票对一遍。
4. tern 的数 ÷ 发票的数，是个接近常数的比例吗？是 → 第 5 类，查 `costMultiplier`。
5. 剩下的差 ≈ 账期头尾某一天的量？是 → 第 6 类，时区边界。
6. 剩下的差集中在长会话、子代理、被 Ctrl+C 打断的任务上？是 → 第 1 类，中断计费。逐条确认只能看面板的「最近请求」表。
7. 缓存命中率明显低于实际体感？是 → 第 3 类，上游没回显缓存字段。
8. 全都不是 → 这时候才值得怀疑 tern 算错了。把区间、`--by model` 的输出、和发票明细一起记下来，附上 `tern check` 的输出。

## 备注

- 第 1、3、4 类的方向都不确定（可能偏高也可能偏低），所以"tern 比发票高"本身不说明任何问题——要先归因。
- 第 2 类是唯一一类补完就归零的，所以它永远排在第一顺位。
- 面板首屏的三条告警（模型被换 / 失败 / 未定价）对应本文的第 4、1、2 类。首屏干净的日子，对账会顺利得多。
- 本文的判据和 `tern usage` 的输出同源：`day` 列按本地日、计价模型优先取上游回显、倍率取自供应商配置。改一处就够。
